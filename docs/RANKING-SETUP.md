# 空の旅ランキングの接続

## Vercelで一度だけ行う設定

1. Vercelで `miracle-mine` プロジェクトを開く。
2. Storage / Marketplaceから **Neon** を選び、**Free ($0)** プランのデータベースを作る。既にNeonがある場合は既存のデータベースを接続できる。
3. `miracle-mine` の **Production** 環境へ接続する。`DATABASE_URL` が自動登録されたことを、値を公開せず環境変数名だけで確認する。`POSTGRES_URL` も代替として対応。
4. プロジェクトの最新デプロイを **Redeploy** する。環境変数の追加は既存デプロイには反映されない。
5. `https://miracle-mine.vercel.app/api/ranking?action=status` が `{"ready":true,"protocol":1}` を返すことを確認。

初回アクセスで `mm_pilots` / `mm_voyages` / `mm_bests` と必要なインデックスを作成する。SQLの手動実行や追加の署名用秘密鍵は不要。接続文字列はサーバー専用。チャット・GitHub・フロント側ファイルに書かない。

設定前やデータベース停止時はAPIが503を返す。ランキング画面は「準備中」を表示し、通常の空の旅・セーブ・秘宝集めは動作する。

公式手順: https://vercel.com/docs/marketplace-storage

## シーズンとお題の生成（v0.18 / protocol 2）

- ルール変更のたびに新しいシーズンをはじめる。シーズンは `server/ranking.js` の `SEASONS` / `CURRENT_SEASON` で定義し、切り替えは定数の追加とデプロイだけで済む。`hidden: true` を付けたシーズンは一覧に出ず、`board&season=N` も404になる（記録はDBに残る）。シーズン1は記録が1件だけなので非表示にしている。表示に戻すときはフラグを外してデプロイする。
- シーズン1（protocol 1、固定のお題列）の自己ベストは `mm_bests` にそのまま残す。シーズン2以降は `mm_season_bests`（`season, uid` が主キー）に保存する。初回アクセス時に `CREATE TABLE IF NOT EXISTS` で作られ、手動のマイグレーションは不要。
- `GET /api/ranking?action=status` は `protocol`、現在の `season`、全 `seasons` を返す。`GET /api/ranking?action=board&season=N` で過去シーズンの上位100機を読める（省略時は現在のシーズン）。`standing` は現在のシーズンの順位。
- 出発（`start`、protocol 2）でサーバーが32bitのシードを発行し、旅の中間情報（`mm_voyages.snapshot`）にシーズン番号と一緒に保存する。クライアントとサーバーは `src/sky-voyage.js` の `voyageGoal(seed, level)` で同じお題列を再現し、ゴールの目標値はサーバー側でこの列と照合する。自己ベストの snapshot にはシードとシーズンは含めない。
- お題列: 因数2〜9の積を、2個×10問、3個×20問、4個×30問、5個×30問の順に抽選する。各セットは積が重複しないよう再抽選し、小さい順に並べる。5個のセットは30問ごとに再抽選して無限に続く。プレイヤーには石の個数を見せず、各段階を空の「領域」（雲の海・夕映えの回廊・星の高み・果ての空、果ての空はⅡ・Ⅲ…と繰り返す）として名前と領域内の進捗で示し、領域が変わるときは全画面のカットインで「気流が変わり、お題は小さな数からまた高くなる」ことを伝える。
- 更新前のクライアント（protocol 1）が出発すると `VERSION` を返し、ゲームは「更新が必要」と案内する。ランキング不参加の旅はクライアント側の乱数シードで遊べる。
- 第6章の盤面: 石は0〜9。お題切り替え時に盤面を書き換える処理は廃止し、補充される石だけを一定確率で現在のお題の因数に寄せる。×で0を含む経路は「消す」扱い、1は積を変えない。ひらめきは5個まで探索する。
- 秘宝の累計飛距離の基準は 300 / 4,000 / 20,000 / 45,000 / 160,000 / 300,000 m。旧基準で獲得済みの秘宝はセーブに保持され、基準の引き上げで失われない。

## ゲーム仕様

- 全30ステージクリア済みの工房でのみ参加を案内。既存の端末セーブは参加資格として受け入れる。過去のクリアはサーバー検証しない。
- 完成機体に20文字以内の名前を付ける。各セーブにランダムな秘密の認証キーを保持し、サーバーからUIDを発行。DBにはキーのSHA-256のみを保持。登録リクエストの再送でも同じUIDが返る。
- 出発時の名前・色・翼・プロペラ・装飾を記録。画像自体はアップロードせず、既存素材と選択値から再描画。
- 旅IDとサーバー発行シードによる目標系列（protocol 2）を使用。各ゴールの連番・目標値を検証し、サーバーが飛距離を加算。
- ゲームの並行エフェクトを維持するため、目標が切り替わる前に完了した、同じ目標に属する並行成功も受理。次の目標は既存のゲーム同様、成功件数を基準に進む。
- 一手単位の通信、操作ログの保存、盤面再現は行わない。改造クライアントからの合法な成功通知や自動解答は防止範囲外。
- 通信はローカルの永続送信キューから順に実行。次の目標は応答を待たない。タイムアウト・一時的な通信失敗は再送し、既に受理した連番は二重加算しない。
- 帰還/蒸気切れの終了通知まで受理した旅のみ自己ベストを更新。未完了の旅は順位に載らない。再読み込みで中断した未帰還の旅は対象外。帰還済みの未送信キューは再読み込み後も再送する。
- 不整合のある旅のみランキング対象外。通常のセーブ・秘宝・ローカル飛距離は変更しない。
- シーズンごとに1 UIDにつき自己ベスト1件、公開は上位100機。自己ベスト未更新なら過去の名前・デザインを維持。同距離は先の達成が優先。
- 操作ログは保存しない。旅の中間情報は1 UIDにつき直近約10件に抑え、新しい出発時に48時間を過ぎた当該UIDの旅を削除。未再訪UIDの期限切れ行は自動スケジュール削除ではなく、次回出発時に削除する。
- 端末のデータを消すと認証情報も失われる。ログイン・端末間復元は今回の対象外。

## 開発・検証

- `npm ci`
- `npm test` — 実際のPostgres互換SQLをPGliteで検証。Neon接続先をテストで変更しない。
- `npm run build`
- `node scripts/preview-ranking.mjs` — メモリ上の一時DBでランキングを確認（本番で使用しない）。
- 通常の `npm run preview` は静的プレビュー。ランキングAPIは含まれない。

本番はルート `api/ranking.js` のVercel Functionが `server/ranking.js` を呼び、Neon HTTPドライバーで永続化する。`src` のみを静的コピーするデプロイではAPIが配置されないので注意。
